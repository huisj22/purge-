## 发现的问题

### P3-01 · 组装顺序与文档不符 — VERIFIED

`ARCHITECTURE.md` 与 `PRODUCT_SPEC.md` 写的是「全局在前、工作区在后」。实际 `compose()` 遍历的是 `list()` 的返回值，而 `list()` 按 **id 字典序**排序（`rules.ts` 的 `sort((a,b) => a.id.localeCompare(b.id))`）。
测试断言 `["proj","style"]` 恰好是字母序，所以测试通过但语义是错的：id 为 `a-workspace-rule` 的工作区规则会排在 `z-global-rule` 前面。
影响：规则文本顺序不稳定/不可预期，但不会丢规则。属文档与实现不一致（P3）。

### P3-04 · 技能扫描的总体积检查是 O(n²) — CODE_CONFIRMED

`skills.ts` 在遍历每个文件后执行 `out.reduce((n,f)=>n+f.size,0)`，文件数 n 时是 O(n²)。200 文件上限下可接受（~2 万次加法），但属于无谓实现。

### 规则冲突

当前**没有**冲突检测：两个规则 id 不同但标题相同、内容互相矛盾时，两者都会进入组装结果。`PRODUCT_SPEC` 里「冲突」一词只在配置中心章节出现，规则中心并未承诺，故记为已知限制（不是缺陷）。

### 技能依赖

`requires` 只做格式检查（正则），不校验真实可用性。导入时给 `unknown_requirement` 警告。**没有**依赖图或循环检测——`PRODUCT_SPEC` 承诺「依赖可达性」，当前未实现（NOT_VERIFIED → 视为未实现能力，记为 P3-14）。

## 安全边界说明

「可执行内容告警」是**提示**，不是隔离。Purge+ 不执行技能内容（只存文件、只组装文本），因此当前风险是「用户把可疑脚本导入后自行运行」。这一点必须在文档中说明，不能宣称"已做安全防护"。

## 结论

规则/技能的围栏与校验是真实实现，且比原项目更严（原项目有 `lib/skills.js:80` 漏 import `fs` 导致软链保护失效）。待修：组装顺序（P3-01）、依赖校验缺失（P3-14）、O(n²)（P3-04）。
