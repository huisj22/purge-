# B10 · Recovery 审计（最高优先级模块）

范围：`src/recovery/{snapshot,transaction}.ts` + `src/packs/engine.ts` 的调用方式

## 逐条回答必答问题

### 1. Snapshot 创建后能否证明完整？ — 部分（CODE_CONFIRMED）

`verify(snapId)` 会：① 校验内联 base64 内容的 sha256；② 从对象库取回每个对象并校验哈希。测试 `tests/recovery.test.ts` 覆盖了「篡改对象 → verify 报损坏」。
**缺口**：`capture()` 自身**不做** post-write 校验（写完对象就认为成功）。若写入过程中文件被外部改过一次，快照记录的是读取瞬间的内容（这是对的），但如果对象写入本身被截断，只有事后 `verify()` 才能发现。

### 2. Snapshot 是否可能在创建过程中损坏？ — 可能（CODE_CONFIRMED）

`capture()` 先 `putObject()` 再写 manifest，两步之间进程崩溃 → 留下孤儿对象（有 `prune()` 可清）。`manifest` 行写入 DB 后若对象被删，只有 `verify()` 能发现。**用户视角**：`capture` 返回成功 = 对象已写入（atomicWriteFile 保证），因此"创建返回成功"是可采信的；但"能恢复"仍需 `verify()`。

### 3. Restore 是否可能覆盖更新版本的用户数据？ — 是（设计如此，有风险）

`restore()` 无条件用快照内容覆盖目标。若用户在此之后又改过文件，恢复会**丢掉这些改动**，且没有提示「快照比当前文件旧」。
**缺口（P2-08）**：没有 mtime/哈希回比，也没有"恢复前自动再拍一张"的保护。恢复 = 确定性的回退，用户需自行确认。

### 4. CAS 是否真的能防止状态竞争？ — 不能阻止写竞争（CODE_CONFIRMED）

对象库按内容哈希寻址，`putObject` 对相同内容幂等（先 stat 比对长度），这确实避免了重复存储。但**快照本身没有并发控制**：两个 `capture()` 并发是安全的（不同 snapId）；两个 `restore()` 并发会互相覆盖，后完成者赢（P2-09）。

### 5. 恢复过程中程序崩溃会发生什么？ — 混合状态（VERIFIED）

`restore()` 逐文件执行 `atomicWriteFile`，中途崩溃 → 已恢复的文件是新内容、未恢复的是旧内容，**没有事务边界**。探针 D 用一个可复现的失败（父目录被占为普通文件）证明同一问题：

```
restored: ["a.txt"]   ← 已改
failed:   ["b.txt"]   ← 没改（EEXIST）
aAfter:   "A0"
PROBE_RESULT=PARTIAL_RESTORE_CONFIRMED
```

（崩溃与"文件级失败"在效果上一致：都留下混合状态。）

### 6. 恢复过程中磁盘空间不足会发生什么？ — 混合状态 + 明确报错（INFERRED）

`atomicWriteFile` 写临时文件失败 → 抛 `unwritable`，该文件进入 `failed`，其余文件继续尝试。最终返回 `{restored, failed}`。**不会回滚已恢复的文件**。

### 7. 恢复失败后系统处于什么状态？ — 部分恢复（VERIFIED，见探针 D）

既不是快照状态，也不是恢复前状态。返回结构里能看出哪些成功/失败，但**没有自动回到恢复前**。

### 8. 恢复是否有二次恢复能力？ — 有，但依赖用户（部分）

`restore()` 可重复执行（幂等方向：再次恢复同一快照会覆盖成快照内容）。但失败后要回到"恢复前"状态，需要事先另拍快照——当前 `restore` **不会**自动拍。这是最重要的可用性缺口。

### 9. 是否存在无法检测的数据丢失？ — 存在（P2-08 + P3-13）

- 快照比当前文件旧时覆盖 → 新改动丢失，且无提示；
- 恢复前不自动备份 → 无法回到"恢复前"；
- `SnapshotStore.get()` 只在前 500 条里找（`snapshot.ts:180`）→ 更老的快照**看起来不存在**（`not_found`），用户以为数据没了（P2-05）。

### 10. 用户能否准确知道恢复成功还是失败？ — 部分

返回 `{restored[], removed[], failed[{path,error}]}`，CLI 打印数量并给出退出码（失败非零）。**但不能**回答"我现在处于哪个状态"，也没有"回滚这次恢复"的命令。

## 发现的问题汇总

| Issue | 等级 | 说明 |
| --- | --- | --- |
| P1-03 | 高 | restore 非事务：部分失败留下混合状态，无自动回滚 |
| P2-05 | 中 | `get()` 只查前 500 条快照，老快照不可达 |
| P2-08 | 中 | 恢复前不校验"快照是否比当前旧"，不自动预拍快照 |
| P2-09 | 中 | 并发 restore 无互斥 |
| P3-20 | 低 | `prune()` 只按 500 条快照计算引用，更老快照引用的对象可能被误删 |

> P3-20 与 P2-05 同源：`list(500)` 的硬上限被当作"全部快照"使用。

## Transaction 审计

`tests/recovery.test.ts` 已证明：写入后回读校验、失败整体回滚、外部修改被 verify 抓到、已提交事务拒绝回滚。
**缺口**：`rollback()` 依赖快照恢复，因此继承了上面「非事务」的问题——如果 rollback 自身部分失败，会返回 `failed` 状态并保留现场（有 `rollback.failed` 明细），这一点是正确的（不假装回滚成功）。

## 结论

CAS 与事务的**设计**是对的，`verify()` 也真实有效。但 `restore()` 是"逐文件尽力而为"，与「Recovery Center 必须可证明恢复成功」的目标不匹配——这是本轮最需要修的 P1 之一（P1-03）。
