## 一、必须回答的 18 个问题

**1. Purge+ 是否可以正常运行？**
可以。`node src/cli/main.ts doctor`、`host list/inspect`、`diagnose`、`serve`、`workflow run`、`job add`、`pack plan` 在真实环境与隔离环境中均实际执行成功（Level 5 只读 / Level 3–4 写入）。修复后 197 项测试 + 14 项验收全部通过。

**2. 哪些核心功能已经得到实际验证？**
宿主识别与版本判定（真实 209 MB ASAR）、只读取证与诊断、配置读取与变更拦截、快照创建/校验/恢复（含故障）、修改包 plan/apply/revert、规则与技能、插件安装与能力约束、更新 check/plan/stage/activate、工作流与调度、审计链、API/CLI 契约。→ 见 `REGRESSION_RESULTS.md` 与 `FAULT_INJECTION_RESULTS.md`。

**3. 哪些功能仅通过模拟测试？**
- 所有**宿主写入**（pack apply 到宿主、快照恢复宿主文件）：只在假宿主上验证（Level 4）。
- 更新激活：只在隔离 data-dir 验证，未对真实安装验证。
- 进程遗留状态恢复：用"数据库遗留 running 行"模拟崩溃，未做真实 kill。

**4. 哪些功能尚未验证？**
UI 浏览器渲染/交互、可访问性、移动端；macOS/Linux 全平台；长期稳定性；真实网络下载（仅 file:// 与 http 代码路径未跑真实公网）；Windows 独占文件锁与 ENOSPC。

**5. 是否存在 P0 问题？**
原来有 1 个（API 入口无鉴权 + 跨站写入 + 可绑公网），**已修复并回归**。当前无已知 P0。

**6. 是否存在 P1 问题？**
原来有 4 个（Kernel 启动锁死、Inspector 误报、恢复非事务、插件边界失真），**全部修复并回归**。当前无已知 P1。

**7. 是否存在数据丢失风险？**
仍存在三类，均已降低但不为零：
- 恢复会覆盖快照之后的改动（P2-08，已加 pre-restore 快照作安全网，未加"新旧比较"）。
- 跨进程并发写同一配置无锁（P2-02 只在进程内串行）。
- 插件以宿主权限运行，可删任意文件（P1-04 只能靠信任门约束）。

**8. Recovery 是否经受故障注入？**
是。29 例故障注入中 11 例针对恢复/事务/快照（对象篡改、父路径退化、并发恢复、幂等、缺失路径）。修复后**失败会回滚到恢复前状态**（`rolledBack=true`）。但未做 ENOSPC 与真实崩溃注入。

**9. Update 是否经受中断测试？**
部分。已验证：索引非法、sha 不符、staging 缺失、prune、同版本重复激活备份。**未验证**：下载中途进程被杀、磁盘满、指针写入后崩溃。这三项在报告中标记 BLOCKED。

**10. Plugin 权限边界是否得到验证？**
验证了「声明式能力」有效（越权 `ctx.use` 抛错），并**证实它不是沙箱**（零能力插件可写任意文件）。当前边界 = "插件以宿主权限运行，启用 host 特权插件需显式信任"。

**11. Workflow 是否存在重复执行风险？**
- 同一 run 并发 resume：已修（`conflict`）。
- 不同 run 并发：预期行为，会产生独立执行。
- 崩溃后 resume：已完成步骤不重跑；**未完成步骤会重跑**（无步骤级幂等键，P3-15）。
- 执行器忽略 abort 时：run 会返回 cancelled 但后台 Promise 仍在跑（副作用不可回收），已在代码注释与报告中声明。

**12. Scheduler 是否存在任务重复或状态错误？**
- 重复触发：已测（一个 tick 窗口三次 tick 只执行一次）。
- 失败后状态：修复后保持 `enabled` 并记录 `lastError`（修复前会永久停摆）。
- runNow 不再推进计划时间（已修）。
- 仍缺"取消运行中 job"能力（P3-18，DEFERRED）。

**13. 是否存在并发问题？**
存在，已量化：
- 已修：配置并发提交、并发快照、并发恢复、并发 resume、审计并发追加、Registry 并发发现。
- 未修：跨进程无文件锁；`allowActions` 自解除；插件间无隔离。
- 明确结论：**所有互斥都是进程内互斥**。

**14. 当前最薄弱的三个模块？**
① 安装/发布链路（无安装器/CI/签名）；② Plugins（安全边界易被误解）；③ Observability 的长跑与关联能力。

**15. 当前项目成熟度是多少？**
核心模块 M2–M3，宿主只读能力 M4，交付链路 M1。**整体判定：M2.5（可内部使用，不宜对外发布）**。

**16. Purge+ 是否适合进入下一阶段开发？**
适合，但前提是先把"能安装、能升级、能卸载"这条链路做出来（当前是 M1）。核心机制已经过审计与故障注入，具备继续演进的基础。

**17. 下一阶段最值得开发的功能是什么？**
① 安装器（`install --verify-first`）+ CI 矩阵；② 子进程插件隔离（把 M2 的插件变成真正的边界）；③ 快照/恢复的跨进程锁与"恢复前差异提示"。

**18. 哪些功能现在绝对不应该开发？**
- 宿主归档换包 / 自动关进程（风险最高，且当前连安装器都没有）。
- 任何"降低安全门槛"的能力（关闭审批、隐藏行为、免确认执行）。
- 在插件没有隔离前，做"插件市场/远程安装"。

## 二、三个明确结论

### A. 当前可以放心使用的功能（有证据）

| 功能 | 证据等级 |
| --- | --- |
| 宿主发现 / 版本识别 / 磁盘与进程状态取证 | Level 5（真实环境） |
| 只读诊断与报告落库 | Level 5 |
| 配置读取、差异预演、哈希守卫（拒绝覆盖外部改动） | Level 3 + L2 |
| 快照创建/校验/恢复（单进程） | Level 3（含失败回滚） |
| 修改包 plan（只读预演） | Level 3 + Level 4 |
| 审计链（写入、查询、篡改检测） | Level 1–3 |
| CLI 退出码与 `--json` 输出 | Level 3 + 实机 |
| 规则/技能的围栏导入与备份 | Level 3 |

### B. 可以使用但需要谨慎（明确限制）

| 功能 | 限制 | 后果 |
| --- | --- | --- |
| `pack apply` / 快照恢复（对真实宿主） | 只在假宿主验证；真实写入 BLOCKED | 可能在真实宿主上产生未预期结果；务必先 plan、先快照 |
| 恢复操作 | 覆盖快照之后的改动；不比较新旧 | 可能丢掉较新的改动（P2-08） |
| 更新中心的 activate | 未在真实安装上验证；无签名 | 激活的是数据目录下的版本目录，不影响运行中代码，但状态可能与预期不符 |
| 多实例/多进程 | 全部锁都是进程内 | 两个 Purge+ 同时写同一文件可能互相覆盖 |
| 调度器 | 无退避、无运行中取消 | 高频失败任务每秒重试会被记录但不停止 |
| 插件（privilege=host） | 与宿主同权限 | `--trust` 之后插件可做任何事 |
| API（默认配置） | 无令牌、仅回环 | 本机同源页面可驱动写入 |

### C. 当前不建议使用（原因与后果）

| 功能 | 原因 | 后果 |
| --- | --- | --- |
| 用 Plugins 运行**不可信**第三方代码 | 不是沙箱（探针 H 已证） | 任意文件读写、任意进程内行为 |
| 把 `host` 绑到 `0.0.0.0` | 需要令牌才允许启动（已加守卫），但无速率限制、无 TLS | 局域网暴露无加密的写接口 |
| 依赖诊断的 `level=ok` 做自动化放行 | `unknown` 是常态（快照不可证、进程不可探） | 误判为健康 |
| 把 `allowActions` 当"白名单"长期使用 | 它能自我解除策略（P2-10） | 高危动作被永久放行 |
| 在跨进程场景下用 ConfigCenter 并发写 | 只有进程内锁 | 丢失更新 |
