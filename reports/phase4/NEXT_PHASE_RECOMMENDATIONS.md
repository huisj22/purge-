# 下一阶段建议（NEXT_PHASE_RECOMMENDATIONS）

按"风险 × 价值"排序，前三项是当前最大短板。

---

## P0（立刻做，否则不能对外发布）

### 1. 安装 / 升级 / 卸载链路（当前 M1）

- `install --verify-first`：**先验证环境与产物**（磁盘、权限、Node 版本、宿主可读），再允许任何关闭进程的动作。
- 打包：`npm pack` + 平台脚本；产物带 SHA256SUMS。
- 卸载：默认保留用户数据（`rules/`、`skills/`、`packs/`、`snapshots/`），需 `--purge` 才删。
- CI：至少 Windows + Linux 各一套（`tsc` + `test` + `acceptance`），矩阵化 Node 22/24。
- 验收：新机器按 README 从零到 `purgeplus doctor` 全绿。

### 2. 插件隔离（当前 M2，且不是沙箱）

- 方案 A（推荐）：子进程 + 受限 IPC。宿主只暴露 `capabilities` 对应的 RPC，插件进程无 fs 直连（用 `--experimental-permission` 或独立用户）。
- 方案 B（过渡）：明确"可信插件"定位，UI 在安装时强提示，并在审计中永久记录 `trusted` 事实。
- 无论哪种，都必须有：调用超时（已有）、并发上限、内存上限、崩溃隔离。

### 3. 跨进程互斥

- 引入维护锁（目录互斥 + PID + 启动时间证明，参考原项目 1.6.61 的做法，但要避免"按年龄删锁"）。
- 覆盖：配置提交、快照创建/恢复、更新激活、pack apply。

## P1（下一步）

### 4. 恢复语义增强（P2-08）

- 恢复前计算"快照 vs 当前"差异并展示；若当前内容比快照新，要求二次确认。
- 提供 `restore --to <preSnapshotId>` 一键撤销上一次恢复（数据结构已具备）。

### 5. 策略自保护（P2-10）

- 修改 `allowActions` / 阈值 需要独立确认（例如 CLI 二次输入、API 需 `confirm:"I-understand"`）。
- 审计中把"策略变更"提升为 high risk 事件并在 UI 顶部横幅提示。

### 6. 观测能力补强（M2 → M3）

- metrics 标签索引，支持按 host/job/step 聚合。
- 长跑采样（内存、句柄、DB 大小），提供"72 小时稳定性"证据。
- 日志轮转策略（当前只有行数上限）。

### 7. Scheduler 退避与取消（P3-18）

- 失败退避（指数 + 上限），避免高频失败任务打满。
- 运行中取消（复用 workflow 的 AbortController 机制）。

## 明确不要做

| 项 | 理由 |
| --- | --- |
| 宿主归档换包 / 自动重启宿主 | 风险最高；在安装器与跨进程锁完成前不做 |
| 任何"降低安全门槛"的能力 | 与 MASTER PROMPT §07 冲突 |
| 插件市场 / 远程一键装插件 | 在沙箱与签名前，等于分发任意代码执行 |
| 云端多租户 | 与单机运维定位冲突 |
| 为了让指标好看而放宽 `unknown` 判定 | 正是本轮修掉的核心问题（P1-02） |
